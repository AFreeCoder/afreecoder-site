# Deployment

## Release Target

- Release branch: `main`
- Release environments: production only
- Production URL or health endpoint: `https://afreecoder.dev/`
- Staging URL or health endpoint: none documented
- Owner or escalation contact: repository owner

## Trigger

- Deployment trigger: push `main` to GitHub — Cloudflare Workers Builds is connected to
  this repository and deploys automatically (~3 minutes after push; verified 2026-06-10,
  deployment `a507f66b` appeared without any manual deploy).
- **Failed builds leave NO deployment record.** `wrangler deployments list` staying quiet
  after a push means the build was triggered but failed (e.g. the 3 MiB size limit) — check
  the Cloudflare dashboard → Workers Builds history, do not conclude the integration is
  missing.
- Manual fallback deploy (emergency only; the next push will overwrite it):

```bash
pnpm run deploy
```

(`pnpm deploy` without `run` hits pnpm's workspace-deploy subcommand and fails.)

- Expected deployment duration: 2–4 minutes (build) + seconds (upload).
- Concurrency or deploy-lock behavior: none documented in this repository.

## Runtime Architecture

- Runtime units: Cloudflare Worker generated by OpenNext for Cloudflare.
- Reverse proxy or edge layer: Cloudflare.
- Databases and persistent stores: none documented.
- Caches, queues, workers, scheduled jobs, or background processors: none documented.
- Important domains: `afreecoder.dev`.
- Runtime config files:
  - `wrangler.jsonc`
  - `open-next.config.ts`
  - `next.config.ts`
  - `package.json`

## Pre-Deploy Checks

Run these before push or deployment:

```bash
pnpm test
pnpm lint
pnpm build:next
pnpm run build:cloudflare
```

Then verify the worker bundle locally — `next dev` cannot catch Workers-runtime-only
failures (e.g. `node:fs` use, missing modules):

```bash
npx wrangler dev --port 8787 --local
curl -s -o /dev/null -w "%{http_code}" http://localhost:8787/
curl -s -o /dev/null -w "%{http_code}" http://localhost:8787/writing/go-file-lock
```

If any check is intentionally skipped, record the reason and risk before deployment.

## Size and Runtime Constraints

- Free-plan Workers limit: **3 MiB gzip** per script. Current usage after the 2026-06-10
  release: ~2.70 MiB gzip — adding heavy dependencies can break deployment.
- Inspect bundle composition with `.open-next/server-functions/default/handler.mjs.meta.json`
  (esbuild metafile; group `inputs` bytes by package).
- Known trap: turbopack externalizes subpath imports (e.g. `shiki/core`) to the package
  main entry, so OpenNext bundles the full package. Heavy data (grammars, article bodies)
  must be inlined via generated modules: `pnpm gen:highlight`, `pnpm gen:bodies`.
- The Workers runtime has no filesystem: never call `node:fs` in request-time code paths.
  `layout.tsx` uses `cookies()`, so every page renders dynamically at request time.
- After `pnpm sync:writing`, regenerate bodies (`gen:bodies` runs automatically in that
  script) before deploying.

## Backup Requirements

- Backup trigger: no runtime database backup is required because the site has no documented persistent data store.
- Backup artifact or metadata: the previous Git commit on `origin/main` and the previous Cloudflare Workers deployment.
- Backup location: GitHub history and Cloudflare deployment history.
- Sanity check: confirm `origin/main` points to the pre-release commit before push, and confirm Cloudflare retains prior deployments for rollback.
- Retention policy: Git history is permanent unless rewritten; Cloudflare deployment retention follows platform policy.
- What failure means: if a previous commit or platform rollback target cannot be identified, stop before production deployment.

## Rollback and Recovery

- Fastest service recovery path: roll back to the previous Cloudflare Workers deployment from the Cloudflare dashboard.
- Previous-version or artifact rollback path: revert the release commit on `main`, push the revert, and let Cloudflare redeploy.
- Database restore path: not applicable; no database is documented.
- Migration rollback path: not applicable; no migrations are documented.
- Actions requiring explicit confirmation: force-push, deleting deployments, changing Cloudflare routing, credential rotation, or any destructive recovery action.
- Verification after recovery: open `https://afreecoder.dev/`, check key routes, and confirm Cloudflare deployment status is healthy.

## Monitoring During Deployment

- CI/CD status command or dashboard: Cloudflare Workers Builds dashboard for `afreecoder-site`.
- Runtime version check: compare the deployed Cloudflare build commit with the pushed Git commit.
- Health check:

```bash
curl -I https://afreecoder.dev/
curl -I https://afreecoder.dev/products
curl -I https://afreecoder.dev/writing
```

- Log checks: Cloudflare Workers logs or build logs for boot, routing, asset, or OpenNext errors.
- Resource checks: Cloudflare dashboard should not report worker errors or deployment failures.
- Business or admin checks: manually open the home page and verify product cards, writing list, theme toggle, and navigation.

## Success Criteria

A deployment is complete only when all required criteria are true:

- Production runs the expected Git commit or Cloudflare deployment.
- Cloudflare build/deploy session completed successfully.
- Previous-version rollback target is available.
- Runtime health checks pass.
- Critical logs are clean enough for the release risk.
- Home page, product cards, writing list, theme toggle, and navigation work in production.

## Failure Handling

- Failure before live impact: stop, collect build/deploy logs, fix forward, and do not mark release complete.
- Failure after live impact: prioritize Cloudflare rollback to the previous deployment, then verify production health.
- When to stop and ask: rollback target missing, DNS/routing changes required, force-push required, or destructive action needed.
- When to recover immediately: the new deployment is live and visibly breaks core pages.
- Evidence to collect: failing command, Cloudflare build/deploy URL or timestamp, response status, screenshots, and relevant logs.
