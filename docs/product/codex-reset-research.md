# Codex 重置监控：调研与内容方案

调研日期：2026-09-18。范围：公开重置公告、额度恢复与可保存重置次数的区别，以及相关产品的信息组织。目标读者：关注 Codex 动态、等待额度恢复的日报读者。

本轮先做研究与方案。此前基于参考截图制作的日历版本保留为本地未发布草稿，不作为最终方向。当前明确约束只有左侧栏目导航、右侧内容；内容区重新设计，不依赖日历。

## 用户确认的优先级

用户进一步明确：关心两件事——下一次额度重置是什么时候、重置卡发过几张；更关心近期是否有重置。以此为最新设计依据，覆盖下文早期“事件档案优先”的建议。

## 结论（按最新反馈调整）

首屏采用两个重点区域：较大的“下一次额度重置”与较小的“近期重置卡”。下方只放与这两件事有关的最新动向。完整历史、来源过程与概念说明按需展开，不占主要位置。

下一次重置：有明确预告就显示预计时间/窗口、适用范围、最新进展与原帖；只有暗示时说明暗示内容及没有明确时间；尚无预告时显示“暂无明确预告”，并将最近一次已完成的时间放在旁边帮助判断消息新旧。没有依据时不制造倒计时或精确概率。已过预告窗口仍需等待确认。

重置卡：先显示所选近期范围内已核实的公开发放数量，再逐次显示每次几张、何时宣布/确认发放、适用对象。发卡公告条数不等于卡数；不同人群的活动不能简单相加成每个人都能领到的总数。公共页面不把公开发放统计称为“你的可用余额”。未确认到账的预告单列，数量不明确则明确写出。

暂定近 7 天为默认近期范围，支持查看近 30 天；这是设计建议，用户未指定时间范围。若尚未补齐历史或采集有缺口，显示“已收录”数量及覆盖时间，不把缺失数据写成 0 张。

最新动向：仅展示重置预告、完成确认、发卡、补偿；一行结论 + 时间 + 原帖。与下一次重置无直接关系的产品更新仍留在“AI 热点动态”。历史记录位于“查看全部记录”，不以日历作为主要展示。

这是基于公开资料、竞品观察和用户明确偏好的设计判断，尚未经过可用性测试。

## 对事情本身的理解

1. 个人额度窗口有账户自身的恢复时刻。官方文档将 `resetsAt` 与额度窗口、使用率一起返回。这不是公众共享的下一次重置时间。
2. 可保存的重置次数是另一种数据。官方接口单独列出可用次数、发放时间及到期时间；有可用次数不等于已经使用，也不等于额度已经恢复。
3. 临时统一重置依赖公开公告。Tibo 的历史帖存在“将重置”“正在传播”“已完成”等不同阶段。公共网站能确认的是公告与适用范围，不能据此确认每一位访客账户到账。
4. 补偿、额度消耗优化和服务恢复也不能自动算作一次全局重置。同一次事情的原帖、引用和转发不能重复计数。
5. 公告时间、预计执行窗口、完成确认时间、本站首次发现时间、最近核验时间是不同的字段。

依据：[官方账户限额与可用重置接口](https://developers.openai.com/zh-Hans/docs/app-server)、[官方用量说明](https://learn.chatgpt.com/docs/pricing)。

核对过的历史原帖：

- [9/8 完成确认](https://x.com/thsottiaux/status/2097174560412246215)：北京时间 2026-09-08 12:05:53。
- [9/12 预告](https://x.com/thsottiaux/status/2098612714704891959)与[完成确认](https://x.com/thsottiaux/status/2098685367058612394)：属于同一次事件，完成确认在北京时间 16:09:17；不能将新闻原始发布时间 11:20 当作完成时间。
- [9/10 补偿公告](https://x.com/thsottiaux/status/2097752790177370535)：针对受影响时段使用过保存重置次数的用户，不是一次全员额度完成重置。
- [Tibo 关于日程的回复](https://x.com/thsottiaux/status/2097175062566846501)：没有给出固定重置日程。不能把历史间隔当成承诺。

### 影响设计的发现

- 各站覆盖范围和计数定义不同。公告数、完成确认数、独立事件数不是同一指标。
- NextReset 声明使用 Codex Resets 的公共数据作为部分上游。多个站点出现同一条消息不等于多个独立证据。
- [NextReset 预测说明](https://nextreset.ai/forecast/)承认其 24 小时预测在披露的历史回测中未超过简单基准，且信号权重并未因此得到验证。因此暂不引入精确概率。
- 竞品中可以同时出现最新摘要与较旧的历史说明。本站应从同一个已核实事件模型生成首屏、列表、历史摘要，避免各区块分别维护事实。
- 社区讨论中有人分不清统一重置与自己的周周期，也有人反馈保存次数消耗后结果不符合预期。[GitHub 用户报告](https://github.com/openai/codex/issues/44443)、[Reddit 讨论](https://www.reddit.com/r/codex/comments/1whvec6/any_hope_for_reset/)。这些属于需求线索，不能当作已证实的系统缺陷，也不能据此估计问题发生率。

## 早期结构分析：供后续细化参考（优先级以上文最新反馈为准）

### 1. 顶部：当前进展

主标题“Codex 重置监控”，副说明“统一重置、重置次数发放与额度相关公告”。首屏最显著位置是一句有证据的结论，而不是大数字或空日历。

状态示例（示例文案，不是对当下实时状态的断言）：

- 暂未发现新的重置预告：截至核验时间，已覆盖来源中暂无新预告。
- 已有重置预告，等待执行：原帖预计的时间窗口、适用范围、来源。
- 已宣布开始，等待完成确认：不把“正在执行”写成“已完成”。
- 官方已确认完成：明确确认时间与适用对象，入口为“查看本次经过”“查看我的用量”。
- 预告窗口已过，尚未确认：倒计时归零不自动转成功。
- 来源检查暂有延迟：继续显示上次确认结论及其时间，不能声称“暂无新消息”。

“最近一次完成确认”和“当前是否有新预告”独立显示。否则一次 6 天前的重置会使当前状态永久呈现“已重置”。

### 2. 紧接着：最近确认的一次重置

紧凑横条：确认时间、距今时长、适用范围、自动生效或需手动使用、查看来源。相对时间作为辅助，绝对时间始终可见。

原文没有说清的范围标“未明确”，不自行扩大成全员。仅有发放预告时用“宣布发放”，不能写成“已到账”。

### 3. 主体：按事件归并的记录流

默认倒序，筛选“全部 / 统一重置 / 重置次数 / 异常与补偿”。每条先显示事件结论、当前阶段、适用人群、读者要做什么，以及最近一条证据时间。

展开后在同一条记录里看全过程，例如：

- 9/12 11:20：官方预告；保留原文时间窗口及不确定性。
- 9/12 16:09：官方确认完成。
- 两条来源归为一次事件，不计两次重置。

记录可以跨日演进；不按日期格子拆散。默认展示简洁摘要，原文摘录、中文解释与相关日报通过展开查看。

### 4. 辅助栏：与我有什么关系

用很短的说明区分统一重置、可保存次数、个人周期恢复。提供官方用量页入口。历史统计在采样足够且来源覆盖清楚后再加入，最多展示已核实次数、历史间隔范围和覆盖说明。

移动端依次为当前进展、最近确认、记录筛选与记录流，辅助说明折叠到下方。

## 风格方向

沿用本站暖白纸面、墨绿强调色和清晰中文排版。用留白、细线、时间与状态标签组织内容；主结论醒目、证据就近。无需暗色终端、人物神化插画、概率仪表盘或大面积月历。左侧保留“AI 热点动态”“Codex 重置监控”两个栏目。

## 后续实现要求

- 原热点采集与展示保持正常，重置记录是同一来源上的专门整理视图。
- 将事件类型、进展阶段、适用范围、是否需要操作分开建模。关键词只能召回候选信息，不能认定完成。
- 保存对应原帖时间、发现与核验时间；监控状态由来源采集结果决定，不能用网站数据同步成功冒充原帖核验成功。
- 来源缺口与无新消息分开；X 无法读取时保留最后已核实状态。
- 预告到期不会自动确认；撤回与事实更正应同步影响首屏与事件记录。
- 不接入读者账号、不读取个人余额、不自动使用重置次数。
- 首版不实现概率预测、投票、日历或额外通知渠道。

首版验收重点：读者在首屏能辨认“是否有新进展”“这次对谁有效”“需要做什么”；从一条事件能追溯完整证据；数据源异常时不会给出虚假的确定结论。
